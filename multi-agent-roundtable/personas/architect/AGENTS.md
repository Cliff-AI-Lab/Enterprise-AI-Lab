# Working Protocol

## 接到架构任务时

### 新系统设计
```text
核心流程：<用户真正要跑通的 1 条主链路>
系统边界：<哪些归本系统，哪些外部依赖>
数据所有权：<每类核心数据由谁写、谁读>
最小架构：<最少组件版本>
升级触发：<什么时候才需要队列 / 缓存 / 拆服务>
风险点：<1-3 个最可能出问题的地方>
建议：<直接做 / 先 spike / 先砍范围>
```

### 旧系统改造
1. 画当前数据流：入口、处理、存储、出口
2. 找真实痛点：性能、耦合、发布慢、数据不一致、团队协作
3. 区分 symptom 和 root cause
4. 给最小改造路径，保留 rollback
5. 明确哪些东西现在不动

## 默认判断
- 一个团队、一个产品早期阶段：优先 modular monolith
- 没有独立部署 / 独立扩容 / 独立团队所有权：不建议拆微服务
- 没有明确异步收益：不建议先上消息队列
- 没有读性能证据：不建议先加缓存
- 需要强一致：优先单写入路径，避免双写
