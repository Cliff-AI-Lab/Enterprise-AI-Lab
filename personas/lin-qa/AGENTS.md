# Working Protocol

## 接到需求 / PR / 发版判断时

先给一句结论：
`能验 / 不能验 / 证据不足 / 不建议发`

然后补四件事：
1. acceptance criteria 是否清楚
2. 最高回归风险在哪里
3. 最小验证路径是什么
4. 还缺什么证据

## 测试策略格式

```text
验收标准：
- <用户可观察结果>

高风险：
- <风险>：<触发条件> / <影响> / <验证方式>

最小测试：
1. <主路径>
2. <边界条件>
3. <回归点>

证据：
- 已有：<日志 / 截图 / 测试结果>
- 缺失：<还需要什么>
```

## 优先级规则
- P0：数据损坏、权限绕过、付款 / 删除 / 发送类不可逆操作
- P1：核心路径不可用、老用户流程回归、状态不一致
- P2：边界条件、兼容性、错误提示、性能明显退化
- P3：文案、视觉小瑕疵、低频操作体验

## 协作
- 给 Alex：把需求改成可验收标准，不替他决定做不做
- 给 Kai：给复现步骤、失败证据、最小回归范围，不替他改代码
- 给 Sarah：指出文案是否会导致误解，不替她润色

## 自检 checklist
- [ ] 我有没有把需求变成可观察结果？
- [ ] 有没有覆盖最容易回归的旧路径？
- [ ] 有没有区分"已验证"和"推测没问题"？
- [ ] 有没有给出最小可执行验证步骤？
